# Аудит расписания, посещаемости и отработок EdCRM

Дата: 2026-08-04
База: `c6ec1aaec3617d01b3b78e29576ecb88c541cecd`

## Объём

Проверены схема Supabase, CRM администратора, кабинет преподавателя, кабинет родителя, notification outbox и MAX webhook/worker. Визуальный capture временно заблокирован ошибкой runtime встроенного браузера; выводы ниже подтверждены кодом и схемой, но не являются полной accessibility-проверкой.

## Текущий путь пользователя

1. Администратор задаёт группе строку расписания, которая преобразуется в `group_schedule_rules`.
2. Занятия появляются в `lesson_sessions` независимо от правил; штатного materialize-процесса нет.
3. Преподаватель выбирает произвольную группу и дату, после чего может создать/запустить session и сохранить boolean-посещаемость.
4. Родитель видит повторяющийся шаблон и вычисленную дату следующего занятия, но не фактические `lesson_sessions`.
5. MAX умеет исходящие уведомления только о выставленном счёте и self-service «Мои счета».

## Сильные стороны

- Есть разделение шаблона расписания (`group_schedule_rules`) и факта занятия (`lesson_sessions`).
- Attendance уже связывается с session и доступна родителям/ученикам через RLS.
- MAX использует outbox, проверенную привязку guardian account и безопасный worker.
- Учитель ограничен своими группами на уровне целевых RLS-политик.

## Критические UX и data-flow риски

1. `lesson_sessions.status = moved` не хранит новую дату или связь с новой session — невозможно показать перенос как один логичный факт.
2. Unique `(group_id, lesson_date)` запрещает два занятия группы в день и усложняет дополнительные/отработочные занятия.
3. Attendance хранит только `is_present`; невозможно различить опоздание, уважительный и неуважительный пропуск, ожидание и выполнение отработки.
4. Учитель и администратор имеют две разные реализации журнала с разными конфликтными ключами upsert.
5. По умолчанию все дети отображаются присутствующими даже до фиксации отметки; это создаёт ложные данные при массовом сохранении.
6. Родительский кабинет не учитывает отмены и переносы и может показывать неверное ближайшее занятие.
7. Отработка упомянута на публичном сайте, но не существует как сущность или workflow.
8. Изменение расписания группы удаляет/создаёт rules, но не объясняет, что будет с уже созданными sessions.
9. Outbox связан со guardian/invoice и worker всегда вызывает invoice message builder; групповые и детские события не поддерживаются.
10. В admin schedule нет недельного operational view, быстрых действий «перенести/отменить» и состояния уведомления родителей.

## Accessibility-риски по коду

- Таблицы и двухколоночные grid не имеют подтверждённого mobile reflow.
- Статусы передаются в основном цветом badges.
- Некоторые интерактивные строки таблицы не являются ссылками/кнопками.
- Используются browser alerts вместо единого feedback pattern.
- Визуальный focus, порядок tab и контраст требуют отдельной browser-проверки.

## Целевой контур

- Rule отвечает за повторение; materialized `lesson_session` — единственный источник фактического календаря.
- Перенос создаёт новую session со ссылкой на исходную, исходная становится `moved`.
- Attendance получает явный status; пропуск может породить makeup request/assignment.
- Makeup assignment связывает исходный пропуск и целевую session, включая session другой группы.
- Один roster-компонент используется администратором и учителем.
- Родитель читает фактические sessions и статусы отработок.
- Любое изменение через server operation атомарно создаёт outbox rows для guardians группы или конкретного ребёнка.
- MAX worker строит сообщение по `template_key`, а меню показывает ближайшие занятия детей.

## Реализованный контур

- CRM администратора: недельные адаптивные карточки, формирование конкретных занятий на 12 недель, добавление внепланового/пробного занятия, перенос/отмена с причиной, проверка конфликта кабинета/преподавателя, состояние MAX и очередь отработок.
- Журнал: один компонент для администратора и преподавателя, статусы «не отмечено / был / опоздал / уважительный пропуск / пропуск без причины», причина и комментарий.
- Отработка: запрос родителя связан с исходным пропуском; администратор выбирает целевое занятие; преподаватель видит гостя; присутствие автоматически завершает отработку.
- Родитель: фактические занятия, отмены/переносы, последние отметки и статус отработки вместо вычисления ближайшей даты только по rule.
- MAX: сохранён прежний invoice workflow, добавлены адресные события нового занятия, переноса, отмены, пропуска и отработки, а также guardian-scoped команда «Расписание» ровно на ближайшие 7 дней.
- Доставка: outbox защищён от дублей по получателю/ребёнку/занятию/шаблону, запускается Vercel Cron каждые 5 минут через `CRON_SECRET` и повторяет временно неуспешную отправку до трёх раз с возрастающей задержкой.
- Доступ: staff API ограничивает преподавателя его группами; parent API начинает выборку с `guardian_users → student_guardians`; RLS отработок не раскрывает учителю чужие группы.

## Ограничения проверки

- Встроенный браузер не подключился из-за runtime-ошибки, поэтому визуальный capture и полноценная keyboard/accessibility-проверка не выдаются за выполненные.
- Локальная Supabase не запущена: Docker daemon недоступен. Миграция покрыта статическими контрактными тестами, но перед production rollout должна пройти на staging-базе.
